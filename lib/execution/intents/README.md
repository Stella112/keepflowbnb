# Read-only transaction intent infrastructure

These modules prepare and record authenticated single-stock intents. They never authorize, sign or submit a transaction. `executionAvailable` is always false, even if deployment flags are changed. No wallet signing or broadcast RPC is present. No budget is reserved: a read-only intent is not a spending permission or committed purchase.

`POST /api/intents` takes `{requestId,ticker,provider,amount}`; wallet identity derives exclusively from an existing opaque authenticated identity session and its verified linked wallet. HTTPS or localhost and same-origin checks are required. Strict input validation rejects caller-supplied wallets, calldata and authority. Real portfolio reads, personal policy, quote freshness/slippage policy, quote construction and actual provider simulation run before a READY_READ_ONLY result. Quote, token addresses/decimals, spender, exact input, minimum receive, approval and swap calldata, chain, policy and wallet snapshot are persisted. Calldata is excluded from HTTP responses; no UI can submit the stored transaction through these endpoints.

The 15-second timestamp is a local preflight freshness limit, not a documented provider expiry. A future write integration must obtain renewed explicit owner authorization and re-quote/rebuild/revalidate. It cannot reuse a prior read-only readiness result as permission. Preparation failures are BLOCKED; a preparation interrupted for over five minutes is fenced as BLOCKED when its owner reads it.

`GET /api/intents/[id]` returns private status and append-only revision events. `POST /api/intents/[id]` accepts only `{hash}` for reconciliation of a transaction submitted externally by its owner. Matching requires verified BSC chain, exact sender, destination, calldata and native value. A previously mined transaction cannot satisfy a newly created intent: receipt block timestamp must be at least the exact intent creation timestamp, with zero clock-skew tolerance. This can conservatively reject an otherwise relevant transaction when the application clock is ahead; it never admits older transactions by invented tolerance.

At least three block confirmations and matching canonical block hash are required before classifying mined success/revert. This is a confirmation threshold, not a claim of irreversible consensus finality. Successful reconciliation additionally checks net funding debit equals the pinned input, stock Transfer receipts meet minimum receive, actual stock balance at the receipt block supports receipt, and canonical hash is unchanged after the balance read. Outcome UNKNOWN is retained on RPC errors, absent transactions, inconsistent blocks or reorganizations; unmined/underconfirmed transactions are PENDING. No unknown state causes a spending retry. A matching confirmed revert is REVERTED; mismatched token effects are UNVERIFIED, never a success. One matching swap hash can bind to only one intent globally. Terminal state and prepared metadata are immutable and revision updates use transactional CAS.

Tests use explicitly synthetic adversarial RPC/log fixtures, never real transaction proofs. No successful provider simulation, wallet signature, mainnet submission or actual ownership increase was established by these unit tests. Pending approval confirmation/requote and actual browser signing remain separate unimplemented write-path requirements; do not claim the full mandate complete.
