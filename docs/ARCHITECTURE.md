# Architecture

Current implementation: Next.js on Lightsail with protected server-only Binance credentials, verified read-only discovery/quote/simulation, durable paper accounts and opaque wallet sign-in sessions. Public HTTPS still requires external reachability acceptance. Mainnet signing and broadcasting are disabled. The sections below retain historical implementation milestones; early statements that credentials or paper scheduling were absent describe the initial bootstrap only. See STATUS.md for current acceptance evidence.

## Initial bootstrap (historical)

Next.js App Router and strict TypeScript bootstrap. Branding lives in lib/brand.ts.

`lib/binance/client-core.ts` implements the read-only signed transport and runtime envelope/data validation. `client.ts` guards configuration with `server-only` and records sanitized request metrics. Only the exact official API host is accepted; redirects are refused. Transport tests use injected HTTP responses and never contact Binance. Successful endpoint schemas, discovery, quotes, wallet adapter, persistence and execution remain pending the authentication gate.

The source-only Lightsail deployment uses Node 24.21.0, an unprivileged Next.js process managed by systemd, and nginx on port 80. Next listens on loopback port 3100. Private keys, environment files, Git metadata and local dependencies are excluded from the archive. No production API credentials have been installed. `/api/health` reports application readiness and explicitly unavailable execution. Consumer data remains unavailable until live verification.


## 2026-10-06 — Implemented read-only purchase architecture
Browser -> Next.js server -> signed Binance RWA/quote/build/simulation calls; viem public RPC reads verify BSC token metadata, USDT balance and spender allowance. Exact approval calldata decoded and checked against the verified input amount and quote spender. No private wallet key, signing client or broadcast endpoint in this flow. Quote/build freshness ceiling is a conservative application 15 seconds, not an assertion of the provider's precise TTL. Production does not serve fixture fallback data. Simulation is integrated in the same quote request to avoid reusing stale candidates. The global per-process 20-check/minute ceiling bounds API consumption; it is not a distributed multi-instance limiter. Wallet provider is test-mocked only in the browser verification script.

## Paper engine and ledger
Paper model is a separate path from Binance quote/build/simulation and from any future mainnet execution. It uses nominal virtual USD, exact bigint price/quantity arithmetic with the original supplied decimal precision, and one-USD-micro-unit cash accounting. Buying rounds token units down and cost up within the budget; selling uses the actual stored paper quantity and live indicative price. SQLite BEGIN IMMEDIATE transactions serialize account writes; repeated trade IDs replay the original receipt, conflicting payloads are rejected. The browser preserves request IDs after uncertain network failures on purchase actions. Receipts contain no fake transaction hash or fake blockchain simulation result.
Bell definitions store ticker weights in basis points plus reserve, content hash and fork provenance. Forks are immutable independent definitions; no parent execution permissions. Public definitions are distinct from private browser-account receipts. Sequential baskets retain completed paper legs, stop after a failed/blocked leg, and mark later legs NOT_STARTED. Deterministic rules check max trade, cash reserve and total direct per-ticker exposure; manual paper allocation spends available virtual cash on target shortfalls beyond configured drift and never proposes selling. This is manual rule practice, not scheduled recurring/autonomous execution.

## Scheduled paper maintenance and versions (2026-10-06)
Accounts optionally store an AutopilotPlan with a Bell snapshot, cadence, contribution, trade limit and next due timestamp. The protected tick endpoint selects up to 20 due accounts and fetches a shared live market snapshot once. Each run rechecks its plan and period inside BEGIN IMMEDIATE, credits one virtual contribution, applies sequential contribution-first paper legs, persists an honest receipt, and advances beyond now. Concurrent old-period work is discarded. No automatic sell path exists. Per-account errors are isolated; unavailable prices retain cash. The authenticated server worker runs regardless of browser activity.
Public Bell ownership is cookie-account based. Publication uses an expected version and archives old definitions in bell_versions. Followers remain pinned until explicit ADOPT, which validates their current concentration/reserve policy and records either ADOPTED or BLOCKED. Schedule and personal policy remain unchanged. This is paper behavior, not live permissions or blockchain execution.

## Wallet identity and preview receipts
wallet_accounts links a verified EOA address to a practice account. login_challenges stores one exact, origin-bound five-minute challenge per current account. Recovering signatures is read-only; transactional consumeLogin rechecks expiry and active message before consuming its nonce and choosing the restored account. No wallet private keys or spending delegation are accepted. Public creator attribution is sourced from this verified mapping. preview_receipts stores quote/simulation summaries under account ownership; raw secret headers are never persisted there. Receipt reads are account scoped and return 404 to other sessions.

## QR desktop approval
qr_logins stores a public request ID, originating desktop account, eight-character matching code, origin, expiry, status and an internal approved phone-account reference. The QR encodes only /login/qr/[id], not an account cookie or signing credential. Approval requires the phone already authenticated by the signed-login flow and an exact matching code. APPROVE and FINISH recheck state inside BEGIN IMMEDIATE. FINISH requires the original desktop cookie and explicit desktop action; it consumes the request before switching the desktop cookie to the approved account. Cancel/new requests invalidate older pending/approved requests. Expired records are removed after a day on new-request creation. Existing paper balances are not merged.
